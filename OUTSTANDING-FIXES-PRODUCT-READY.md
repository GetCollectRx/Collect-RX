# Outstanding Work for a Production-Ready Product

> **Status source note:** The phase "Status" lines below are point-in-time snapshots (oldest from 2026-04-22) and do not reflect work done since — including the Stripe Billing/trial-tier system and the marketing/growth-engine (email campaigns, prospect harvesting) under `Collect-RX-main/src/server/marketing/`, neither of which has phase entries here. For **current** launch-readiness status, use [`docs/operations/PATH-TO-DELIVERY.md`](docs/operations/PATH-TO-DELIVERY.md) — it's kept live. Treat this file as a ticket backlog for reference, not a status report.

**Product intent:** The target is a **complete, deployable** CollectRx—something you can run in **staging and production** with a supported database, CI, secrets, monitoring, and compliance work appropriate to handling healthcare-adjacent data. This backlog is **not** “how to stay a demo”; it is the ordered work to get from the current codebase to that bar. (Some copy in older READMEs may still say “POC”; treat this document as the north star.)

**Launch order (A→G):** [docs/operations/PATH-TO-DELIVERY.md](docs/operations/PATH-TO-DELIVERY.md) — Practice → Insurance only; no patient/client payment collection.

**Purpose:** Backlog of **ticket-sized** tasks, grouped by **phase**. Phases are sequential in priority: finish Phase 1 decisions before large Phase 2–3 build-outs; Phase 4+ can overlap once the core path is defined.

**Ticket format:** Each item is sized for a single issue/PR (roughly **0.5–3 days** unless marked **[L]** for larger epics to split further).

> **Context:** The repo currently mixes two stacks (`Collect-RX-main/` Prisma + Vite vs root `src/api` + `src/frontend`). **Phase 1** must resolve what ships as the product.

## Phase 10 — Manual UX / dev-experience audit (2026-08-06)

*Goal: Everything this repo's docs and UI promise, verified by actually running the app end to end — not just by CI passing.*

**Status (2026-08-06):** Triggered by a live walkthrough — Postgres + Redis stood up locally, a generic demo practice seeded, and every core screen driven in a real browser as a practice owner. Found the primary local dev workflow (`npm run dev`) completely broken and one revenue page crashing outright; both were invisible to CI because CI runs the production build, not the dev server. The escalations gap it surfaced (P10-03) turned out not to be a seed-only artifact: auditing real code (P10-04) found the same desync live in production on the two backend paths that actually escalate a claim — including the primary post-call routing path, which had never had a test written against it. **P10-01–P10-07 are all fixed** (commit `9baec99` + follow-ups on `claude/app-testing-requirements-3s2x8o`) — the whole "get a working local instance" cluster (P10-01/02 dev crashes, P10-03/04 escalations desync, P10-05 fictional credentials, P10-06 one-command bootstrap, P10-07 port detection) is closed out. Notably, building and end-to-end-testing the P10-06 bootstrap script surfaced a fourth real bug of its own: `.env.example` shipped `DEV_API_TARGET=remote` uncommented, silently pointing every fresh local setup at the production API. **P10-08 (front-desk role) is now audited and clean** — no bugs found; role scoping holds at both the frontend router and the API layer, verified directly with `curl`, not just inferred from the UI. **P10-09 (admin/platform-admin) is fixed** — at the time, the most severe finding of the whole phase: `platform_admin` was locked out of its own screens on any page refresh, and `auditor` couldn't stay authenticated past login at all, both from the same family of "legacy role string" bugs repeated across four call sites. Fixing it opened two new tickets (P10-13, P10-14) for adjacent gaps found but not resolved. **P10-10 (AR command center / group dashboard / CDCP / reports) is fixed** — two real bugs (an unvalidated `?tab=` param that silently blanked the pre-visit page, and a `/group-dashboard` route guard that didn't reuse an already-correct disambiguation helper in the same file) — and, chasing an intermittent error on `/canadian-2026` down to its root cause, surfaced **P10-15**, which supersedes P10-09 as the most severe finding of this entire phase: a misscoped `router.use(strictLimiter)` in the early-access lead-capture router was silently rate-limiting **the entire `/api` surface** to 10 requests/minute per user, not just the one public form route it was meant to protect — in production this would have made the whole product unusable within seconds of normal use for any moderately active practice user. **P10-15 is fixed.** **P10-11 (claim-detail sub-features) is fixed** — a broken evidence-pack download and a CSV-import column-name gap that silently disabled the entire Denial Hub feature for the one import path (the app's own shipped sample template) it exists to serve; fixing it also surfaced and fixed a real pre-existing test-suite flake (`tests/dsoLoadCapacity.test.ts` failing 15 of 24 hours a day) unrelated to the audit itself but blocking the push gate. **P10-12 (dual-source-of-truth sweep) is fixed** — found the exact pattern it was written to look for: the Priority Queue's own `WorkItem` table never closed a row once its claim resolved, so resolved claims would sit in the queue as "still actionable" forever. **P10-13 is fixed** — on closer inspection this wasn't actually a design question: the grant-checking logic auditors need already existed and was already enforced on real data routes, it just was never called from the two endpoints that build the `practices` list. **P10-14 is closed** — turned out to be answerable from the code itself (two structurally separate token-signing paths, not an inconsistent branch), not a real open question. **Phase 10 is fully closed out**: every ticket opened during this audit (P10-01 through P10-15) is now fixed or confirmed-not-a-bug, with a live-verified repro and a regression test for every real fix.
