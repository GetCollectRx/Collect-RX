- **Desk queue tick error recovery — P0.5, now done** (`src/server/frontDesk/queueEngine.ts`). Read `claimTickLease()` fully before touching anything, per this item's own safety note — the fix below is scheduling-level only and never touches the lease mechanism. Before this pass, a thrown `runDeskQueueTick()` was caught in `startDeskQueueEngine()`'s `fire()` and only logged; the next fixed 60s `setInterval` fire would retry unconditionally, forever, with no backoff and no alert — under a sustained outage (DB down, etc.) that's an unthrottled retry loop with zero visibility.
  - **Backoff:** module-level `consecutiveTickFailures` / `nextTickEarliestAt` state in `queueEngine.ts`. On failure, `nextTickEarliestAt = now + min(15min, 60s * 2^consecutiveTickFailures)` — deliberately `2^N`, not `2^(N-1)`: with a fixed 60s interval, a backoff equal to exactly one interval coincides with the next scheduled fire and skips nothing, so the exponent had to guarantee at least one skipped fire per failure. `fire()` now checks `Date.now() < nextTickEarliestAt` and returns early (a no-op skip, not a reschedule of the `setInterval` itself) when still backing off. A successful tick resets both to zero/none.
  - **Alerting:** new `desk_queue_tick_failing` alert-catalog entry (critical); `dispatchOpsAlert` fires once `consecutiveTickFailures` reaches 3, via the same channel/cooldown machinery as every other ops alert in this repo (SMS/email/webhook, `OPS_ALERT_COOLDOWN_MINUTES` dedup) — no new dispatch mechanism. **Recovery is logged, not alerted**: `dispatchOpsAlert`'s `severity` field is typed `AlertSeverity = 'critical' | 'high' | 'medium'` — there's no 'info' level in this codebase's alert system to page on, and inventing one to push a "resolved" message through the same SMS/email pipe built for incidents would be a real behavior change, not a mechanical one. A `logger.info('[deskQueueEngine] tick recovered after previous failures', ...)` line plus the exposed `lastSuccessfulTickAt`/`consecutiveTickFailures` fields (below) are the recovery signal instead.
  - **Observability:** `getDeskQueueTickHealth()` (new, exported from `queueEngine.ts`) returns `{ lastSuccessfulTickAt, consecutiveTickFailures, lastTickFailureAt }` — single-instance state, same precedent as `vapiCircuitBreaker.getMetrics()` already being single-instance. Wired into `queueHealth.ts`'s `QueueHealthSnapshot` (imported directly — no circular dependency, confirmed: `queueEngine.ts` does not import `queueHealth.ts`), which already backs `/api/health/metrics` via `src/server/index.ts`'s existing `getQueueHealth(prisma)` call — no route change needed.
  - **Stall threshold:** `defaultQueueHealthThresholds()`'s `stallMinutes` default reduced from 30 to 5 (still overridable via `OPS_ALERT_QUEUE_STALL_MINUTES`) — 30 minutes of silent dispatch stall is far too slow to notice on an unsupervised pilot; 5 minutes still comfortably exceeds one tick interval plus this item's own backoff/retry window.
  - Tests: `tests/frontDesk/deskQueueTickRecovery.test.ts` (new — proves backoff genuinely skips the next scheduled fire via fake timers, not just that the counter increments; proves the alert fires exactly at 3 consecutive failures and not before; proves a success after failures resets state and records `lastSuccessfulTickAt`), plus `tests/queueHealth.test.ts` updated for the new snapshot fields and reduced default threshold. Full suite (1533 tests, 8 pre-existing skips) verified green against real Postgres + Redis; typecheck, lint (0 errors), and the production build all pass.
